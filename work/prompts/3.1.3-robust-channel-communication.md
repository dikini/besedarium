# Task 3.1.3: Implement Robust Channel Communication with Timeouts and Enhanced Error Reporting

## Objective

Enhance the reliability and resilience of inter-role communication within sessions by implementing configurable timeouts for channel operations and providing more detailed error reporting for communication failures.

## Background

The current channel communication (`src/runtime/channel.rs`) facilitates message passing between roles in a session. However, it lacks mechanisms to handle unresponsive peers or operations that take too long, and error messages for communication failures could be more informative.

## Requirements

1. **Configurable Timeouts**:
    - Implement timeout mechanisms for `send` operations on channels. If a send operation cannot complete within the configured timeout (e.g., because the receiving end's buffer is full and it's not reading), it should fail with a specific timeout error.
    - Implement timeout mechanisms for `receive` operations on channels. If a receive operation does not get a message within the configured timeout, it should fail with a specific timeout error.
    - Timeouts should be configurable, potentially at different levels:
        - Globally for the runtime.
        - Per session type.
        - Per specific channel or operation (if deemed necessary, though this might add complexity).
    - The default behavior if no timeout is configured should be to wait indefinitely (current behavior), or a sensible default timeout.

2. **Enhanced Error Reporting**:
    - When a channel operation fails (e.g., send error, receive error, timeout, deserialization failure), the `RuntimeError` generated should include more contextual information:
        - `ChannelId`: Identifier of the channel involved.
        - `OperationType`: E.g., "send", "receive".
        - `ExpectedMessageType` (for receive): The type of message that was expected, if known.
        - `ActualMessageType` (for deserialization errors): The type of message that was received but failed to deserialize.
        - `PeerRole` (if identifiable): The role at the other end of the channel.
        - `SessionId`: The session this channel belongs to.
        - The underlying error (e.g., `SendError`, `RecvError` from `tokio::mpsc`, deserialization error).
    - This aligns with Task 3.1.5 (Refine Runtime Error Hierarchy).

3. **Graceful Handling of Failures**:
    - Ensure that when a channel operation fails due to a timeout or other error, the channel and session state are handled gracefully.
    - The error should be propagated appropriately to the part of the system managing the session's logic.
    - Consider whether a channel should be marked as "broken" or "unhealthy" after certain types of persistent failures.

4. **Deserialization Errors**:
    - Improve handling of message deserialization errors. If a message is received but cannot be deserialized into the expected type, the error should clearly indicate this, including the raw bytes or a snippet if possible and safe.

## Implementation Guide

1. **Tokio Timeouts**: Leverage `tokio::time::timeout` for wrapping asynchronous channel operations.
2. **Configuration**: Determine the best way to manage timeout configurations. This might involve changes to session setup or runtime configuration structures.
3. **Error Types**: Define new variants or enhance existing ones in `RuntimeError` (`src/runtime/error.rs`) to accommodate detailed communication errors.
4. **Channel Abstraction**: Ensure that the `Channel` trait and its implementations in `src/runtime/channel.rs` are updated to support these new features.
5. **Testing**: Pay close attention to testing timeout conditions, which can be tricky. Use `tokio::time::pause` and `advance` in tests if appropriate.

## Verification and Testing

1. **Unit Tests**:
    - Test `send` timeouts: e.g., try to send to a full bounded channel that is not being read from.
    - Test `receive` timeouts: e.g., try to receive from an empty channel.
    - Test various error conditions (channel closed, deserialization failure) and verify the details in the `RuntimeError`.
    - Test with different timeout configurations.
2. **Integration Tests**:
    - Create session scenarios where one role becomes unresponsive or slow, and verify that timeouts trigger correctly in the interacting roles.
    - Test how the system behaves when communication errors occur mid-protocol.

## Success Criteria

- `send` and `receive` operations on runtime channels support configurable timeouts.
- Communication-related `RuntimeError` instances contain detailed contextual information as specified.
- The system handles communication timeouts and errors gracefully, propagating them correctly.
- Deserialization errors are reported with useful details.
- The implementation is well-tested, especially for timeout conditions.
