1. **Channel-explicit design**: All communications must specify channel metadata (`CommMetadata`)
2. **Action I/O awareness**: All actions must specify required I/O type (`ActionIOTMarker`)
3. **Type safety**: Proper trait bounds and generic constraints
4. **Backward compatibility**: Existing protocol logic should continue to work with adaptations

#### TChanSend - Channel Send Action

```rust
use crate::foundation::{Role, Message, GlobalProtocol, CommMetadata, ActionIOTMarker, ChanId, MsgLbl};
use std::marker::PhantomData;

/// Global Type: Represents sending a message over a specific channel
///
/// - `S`: Sender Role
/// - `R`: Receiver Role  
/// - `M`: CommMetadata (channel ID and message label)
/// - `Msg`: Message type being sent
/// - `P`: Continuation Global Protocol after the send
/// - `AIO`: ActionIOTMarker specifying required I/O type
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct TChanSend<S: Role, R: Role, M: CommMetadata<C, L>, Msg: Message, P: GlobalProtocol, AIO: ActionIOTMarker, C: ChanId, L: MsgLbl> {
    _sender: PhantomData<S>,
    _receiver: PhantomData<R>,
    _meta: PhantomData<M>,
    _msg: PhantomData<Msg>,
    _protocol: PhantomData<P>,
    _aio: PhantomData<AIO>,
    _chan: PhantomData<C>,
    _lbl: PhantomData<L>,
}

impl<S: Role, R: Role, M: CommMetadata<C, L>, Msg: Message, P: GlobalProtocol, AIO: ActionIOTMarker, C: ChanId, L: MsgLbl> 
    GlobalProtocol for TChanSend<S, R, M, Msg, P, AIO, C, L> {}
```

## Debugging Guide

### Common Issues

1. **Type parameter explosion**:
   - Issue: Too many generic parameters make types unwieldy
   - Solution: Use type aliases and builder patterns

2. **Trait bound conflicts**:
   - Issue: `CommMetadata<C, L>` bounds not satisfied
   - Solution: Ensure `C: ChanId` and `L: MsgLbl` bounds are properly specified

3. **Circular dependencies**:
   - Issue: Global protocol types reference each other
   - Solution: Use proper trait bounds instead of concrete types where possible

4. **Integration with existing code**:
   - Issue: Existing projections/transforms don't work with new types
   - Solution: Create adapter implementations or migration helpers

### Validation Steps

1. **Compile all new types**: `cargo check`
2. **Run existing tests**: Ensure no regressions
3. **Test type composition**: Verify complex protocol compositions work
4. **Check trait implementations**: Ensure `GlobalProtocol` trait is properly implemented
