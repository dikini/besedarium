# Task 1.1.3: Local Endpoint Types Implementation

## Objective

Implement Local Endpoint Types that correspond to the Global Protocol Types from Task 1.1.2, ensuring consistent `IO` parameter handling and `SupportsActionIO` trait integration. These types represent the projected view of protocols from individual role perspectives.

## Prerequisites

- **Task 1.1.1 completed**: Foundation types available
- **Task 1.1.2 completed**: Global Protocol Types (`TChanSend`, `TChanRecv`, etc.) implemented
- **Reference documentation**: Study Local Endpoint definitions in `docs/duality.md`
- **Existing analysis**: Understand current endpoint types in `src/protocol/local.rs`

## Context and Requirements

### Design Principles

1. **Role-specific perspective**: Each endpoint type represents what a specific role must do
2. **IO capability integration**: All endpoints must specify and verify required I/O capabilities  
3. **Metadata preservation**: `CommMetadata` must be preserved from global to local types
4. **Action I/O compatibility**: Local endpoints must enforce `SupportsActionIO` constraints

- `EpSend<IO, Lbl, R, H, T>` in `src/protocol/local.rs`

#### EpChanSend - Local Channel Send Endpoint

```rust
use crate::foundation::{Role, Message, LocalProtocol, CommMetadata, ActionIOTMarker, SupportsActionIO, ChanId, MsgLbl};
use std::marker::PhantomData;

/// Local Endpoint Type: Represents sending a message from sender's perspective
///
/// - `IO`: Session I/O capability, must implement `SupportsActionIO<AIO>`
/// - `M`: CommMetadata (consistent with global view)
/// - `Msg`: Message type being sent
/// - `P`: Continuation Local Protocol for the sender
/// - `AIO`: ActionIOTMarker (consistent with global view), constraining `IO`
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct EpChanSend<IO: SupportsActionIO<AIO>, M: CommMetadata<C, L>, Msg: Message, P: LocalProtocol, AIO: ActionIOTMarker, C: ChanId, L: MsgLbl> {
    _io: PhantomData<IO>,
    _meta: PhantomData<M>,
    _msg: PhantomData<Msg>,
    _protocol: PhantomData<P>,
    _aio: PhantomData<AIO>,
    _chan: PhantomData<C>,
    _lbl: PhantomData<L>,
}

impl<IO: SupportsActionIO<AIO>, M: CommMetadata<C, L>, Msg: Message, P: LocalProtocol, AIO: ActionIOTMarker, C: ChanId, L: MsgLbl>
```

## Debugging Guide

### Common Issues

1. **`SupportsActionIO` trait bound not satisfied**:
   - Issue: Compiler error about IO capability not supporting action type
   - Solution: Ensure IO type implements `SupportsActionIO<AIO>` for the required action type

2. **Complex generic parameter chains**:
   - Issue: Type parameter lists become very long and unwieldy
   - Solution: Use type aliases and builder patterns to simplify usage

3. **Circular trait bounds**:
   - Issue: Traits reference each other causing compilation errors
   - Solution: Carefully structure trait hierarchies and use associated types

4. **Metadata type mismatches**:
   - Issue: `CommMetadata<C, L>` types don't match between global and local
   - Solution: Ensure consistent channel ID and message label types

### Validation Steps

1. **Compile endpoint types**: `cargo check`
2. **Test IO capability constraints**: Verify only valid IO/AIO combinations compile
3. **Integration tests**: Ensure endpoint types work with projection system
4. **Type safety tests**: Verify different channels/actions create distinct types
