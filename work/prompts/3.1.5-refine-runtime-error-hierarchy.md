# Task 3.1.5: Refine Runtime Error Hierarchy and Contextual Information

## Objective

To create a more structured, informative, and user-friendly runtime error hierarchy (`RuntimeError` in `src/runtime/error.rs`) that aids significantly in debugging, error handling, and understanding issues arising during protocol execution.

## Background

The existing `RuntimeError` enum provides a basic level of error reporting. As the runtime becomes more complex with advanced checks (Tasks 3.1.2, 3.1.3, 3.1.4), the error types need to evolve to provide richer contextual information and a clearer categorization of problems.

## Requirements

1. **Clear Categorization**:
    - Review and categorize existing and new runtime errors. Potential categories include:
        - `StateError`: Invalid state transitions, protocol violations related to state.
        - `CommunicationError`: Channel send/receive failures, timeouts, deserialization issues.
        - `SessionError`: Issues with session setup, lifecycle, resource management.
        - `ProtocolMisuseError`: Incorrect usage of protocol constructs by the application.
        - `InternalError`: Unexpected conditions within the runtime itself.
        - `SerializationError`: (Already being improved by 3.1.1) Problems serializing/deserializing messages.
    - The `RuntimeError` enum should reflect these categories, possibly through nested enums or by structuring variant names.

2. **Rich Contextual Information**:
    - For each error variant, identify and include relevant contextual information that would help a developer diagnose the problem. Examples:
        - `SessionId`, `Role`
        - `CurrentState`, `AttemptedActionOrMessage`, `ExpectedStatesOrActions`
        - `ChannelId`, `PeerRole`
        - `OffendingMessagePayload` (or a snippet/summary)
        - Source error (using `#[source]` or `source: Box<dyn Error + Send + Sync + 'static>`)
        - Relevant part of the protocol definition (e.g., state name, transition identifier).

3. **Improved `Display` and `Debug` Implementations**:
    - Implement `std::fmt::Display` for `RuntimeError` to produce user-friendly error messages that are suitable for logging or showing to end-users of the library.
    - Implement `std::fmt::Debug` to provide detailed, developer-focused information, including all contextual data.
    - Ensure messages clearly explain what went wrong, where, and ideally, why or what was expected.

4. **Source Error Chaining**:
    - Properly utilize error chaining (e.g., via the `source()` method of `std::error::Error`) so that the root cause of an error can be traced.
    - This is crucial when `RuntimeError` wraps errors from underlying libraries (e.g., Tokio, Serde).

5. **Consistency**:
    - Ensure a consistent approach to error creation and propagation throughout the `src/runtime/` module.
    - Use helper functions or macros for creating common error types if it improves consistency and reduces boilerplate.

6. **Ergonomics for Library Users**:
    - Consider how users of the Besedarium library will match against and handle these errors. The hierarchy should be intuitive.
    - Provide clear documentation for each error variant.

## Implementation Guide

1. **Iterative Refinement**: This task will likely involve iterating on the `RuntimeError` enum as other sub-tasks (3.1.2, 3.1.3, 3.1.4) identify new error conditions and context requirements.
2. **`thiserror` Crate**: Strongly consider using the `thiserror` crate to simplify the implementation of `std::error::Error` and the `Display` trait.
3. **Collaboration**: Work closely with the implementers of other Task 3.1 sub-tasks to ensure their error reporting needs are met.
4. **Review Existing Errors**: Audit all current uses of `RuntimeError` and update them to the new structure and provide more context.

## Verification and Testing

1. **Unit Tests**:
    - For each error variant, write tests that:
        - Trigger the error condition.
        - Verify that the correct `RuntimeError` variant is produced.
        - Verify that all expected contextual information is present.
        - Check the output of `Display` and `Debug` implementations for clarity and completeness.
2. **Code Review**:
    - Review all error creation sites in the runtime to ensure consistency and completeness of context.
3. **Documentation Review**:
    - Ensure that documentation for `RuntimeError` and its variants is clear and accurate.

## Success Criteria

- The `RuntimeError` hierarchy is well-structured and clearly categorizes different types of runtime problems.
- Error instances contain comprehensive contextual information aiding diagnostics.
- `Display` and `Debug` formats are user-friendly and developer-informative, respectively.
- Error chaining is correctly implemented.
- The refined error types are consistently used throughout the runtime.
- The changes make it significantly easier to understand and debug runtime issues.
